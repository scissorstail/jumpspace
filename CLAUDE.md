# jumpspace: notes for Claude

A visual SSH connection editor (Electron 44 + Vue 2.7 + Rete v1). Servers are nodes, chained nodes are jump hosts, one click runs the right `ssh` command in a terminal inside the app (Git's `bash.exe` on Windows) or in a Git Bash window. Windows + Git Bash is the target; development and CI also run on Linux.

The owner writes Korean: answer in Korean in chat, keep code, commit messages and docs in English. Code comments are mostly Korean; match the file you are editing.

- `README.md`: features, usage, project layout, how ssh is started, tests.

## Rules that matter

- **Nothing user-controlled reaches a shell unchecked.** Every value that ends up in an `ssh` command or config goes through `src/shared/validate.js` (main checks before running; the node settings form shows the same rules while typing); `ssh.js` builds a bash script with POSIX single-quoted values. Passwords travel only as environment variables and are answered through `SSH_ASKPASS` (the generated script is its own askpass). Never put passwords or keys into logs, docs or commit messages.
- **The repository is public (MIT).** No secrets, tokens, real hosts or personal data in files or commit messages.
- **Behavior changes need a test.** After adding a test, break the code on purpose once and see it fail. Never skip or delete a failing test to get green.
- The renderer is sandboxed with a narrow IPC API (`src/preload/index.js`; `src/preload/ipc.test.js` reads the sources and fails when a channel of the preload has no receiver in main or the other way round, when main takes a request past its two sender-checking wrappers, when the page calls something the preload does not offer, or when main reads a value of the page without the function that checks it, see "Values of the page" below). Keep logic that can be pure in `src/renderer/src/utils/` or `src/main/*.js` with tests; components stay thin. Values both processes need (setting defaults and validation, the canvas zoom range) live once in `src/shared/` (no Node modules there).
- **Keep the docs true.** A user-visible change goes into the Unreleased section of `CHANGELOG.md`; a new file in `src/main` or a new node component goes into the "project layout" of `README.md`.
- Saved data (`projects.json`, items are `{ name, data, view?, opened? }`) goes through `normalizeItems` in `src/main/storage.js`. Saves are queued there (one at a time, in the order asked for; a failed one does not stop the next): the renderer saves from several places (`saveProject()` in `Layout.vue`: on locking, on a change of the space list, 0.4 s after the canvas moved) without waiting for each other, and overlapping saves shared `projects.json.tmp`, so the later `rename` failed with ENOENT (seen by the owner, 2026-10-11). The `rename` onto `projects.json` is tried again after EPERM, EBUSY or EACCES (6 waits, about 1.5 s in all): Windows refuses it while anything has the file open, which a test that read the file right after a save ran into once. `createProjectStorage(dir, { renameFile, wait })` takes both for the tests. Old data must keep loading; add a migration there instead of breaking it. `load()` returns `null` only when both `projects.json` and `projects.json.bak` are missing (a first start). A file that is there and cannot be read, with no backup that can, makes it **throw** (one line per file, that nothing was changed, the folder): it used to return `null` for that too, so the app started empty, and the two saves of the first new space wrote over the file and then over its backup (found 2026-10-14 with a cut off file in the real window). The thrown error sets `isProjectLoadFailed` in `Layout.vue` (no save for the rest of the session) and is shown as a message that stays (`toastError(..., { noAutoHide: true })`). The files are never touched, renamed or "repaired" by the app. The message does not repeat the words of `JSON.parse`: they quote the text around the mistake, and the file holds passwords. Main does not end while a save has not ended: `createQuitHold` (`src/main/quit-hold.js`) on `will-quit` prevents the end while `projects.isSaving()` and calls `app.quit()` again when `projects.settled()` is over, after `QUIT_WAIT_LIMIT_MS` (5 s) at the latest, so a disk that hangs leaves no app without a window. With the default setting closing the window ends the app. A save takes a few ms, but while another program has `projects.json` open the rename is tried again for up to 1.5 s, and a window closed in that time ended the app before the save: the change of the lock was lost and `projects.json.tmp` was left (found 2026-10-14 in the real window, with a PowerShell that held the file open for 0.6 s). The page needs no such wait as it is: a window closed 0 to 1100 ms after the press on the lock was saved every time (24 of 24 with 150 nodes, where the page needs about a second before it asks main), because the page is busy with the lock until it has asked and the close waits behind that. An `await` on a real task between the lock and `saveProject()` (a timer, a worker) would open a gap there: the page already says locked, so it would not hold the unload. While a save has not ended a faint ring turns in the header (owner, 2026-10-11; the word *Saving* that stood there first flashed with every save and bothered the owner): `savingCount` in `Layout.vue` goes up before `saveProjects` and down in `finally`. The place of the mark (`.save-state`, first in the toolbar slot, 1rem square) is always there, so the buttons do not move; the `b-spinner` in it has the `v-if`.

## Gotchas learned the hard way

- The popovers (v-tooltip / popper.js 1.x) are moved out of the window by the `arrow` modifier because the arrow element has no styles; it is disabled in `main.js`. Keep it that way.
- Styles of `rete-context-menu-plugin` are scoped (`.item[data-v-x]`); overriding needs a more specific selector such as `div.context-menu div.item`. The menu's own rule (`.context-menu[data-v-x]`: width 120px, padding 10px, margins -20px and -60px) beats `div.context-menu` too; only `#rete div.context-menu` beats it (the `#rete &` block of `context-menu.scss`). So the `padding: 4px` there does not apply, the menu has the plugin's 10px.
- The right-click menus (canvas and node) are the plugin's menu with two additions: `components/editor/context-menu.js`, given to the plugin as `vueComponent` (owner, 2026-10-18, #267: "like a usual menu"; the candidate was found in #116). **Its place**: `menuPlace()` of `utils/menu-place.js` puts the top left corner `MENU_GAP` (2px) right of and below the pointer, and turns to the left or upward where the canvas has no room, so the pointer is always outside the menu at one of its corners and no item is under it. Before, the plugin's margins (taken away by `margin: 0` in `#rete &`) opened it 60px left of the pointer and 20px above it, with *Add node* or *Delete* under the pointer, and a second click there added or deleted a node. The room is the canvas (`#rete`, the parent of the menu), not the window: the terminal panel is drawn over the menu. The plugin's `updated()` runs before ours and pushes the menu into the window (`fitViewport`, with `clientWidth`, which leaves out the border); ours places it from the pointer remembered in `show()` and then cuts it with the plugin's rule once more, so that the next `updated()` of both gives the same place. Two rules that disagree (in a window smaller than the menu) set `x` back and forth in every update, and the page hung. **Closing**: the plugin closes the menu at an item, when the mouse leaves it after being in it (`mouseleave`, then `delay`, 250 ms) and on Rete's `click` and `contextmenu`, and Rete's `click` comes only for a press on `#rete` itself (not on a node, the header or a terminal). With the pointer outside the menu a menu nobody went into stayed open, so `show()` adds a `pointerdown` listener on the document in the capture phase that closes it at a press outside it, and `hide()`, which every way of closing goes through, takes it away: the plugin makes a new menu at every right click and never destroys the old ones. `context-menu.test.js` reads all that from the installed plugin. A node from the canvas menu still goes where its item is pressed (`area.mouse` of Rete), which is now right of and below the right click. `menu-check` of the headless checks goes through each case.
- Rete plugins need `regenerator-runtime` (imported first in `main.js`).
- The look (colors, fonts, Bootstrap overrides for buttons, forms, dropdowns, modals, toasts) lives in `src/renderer/src/assets/theme.scss` as CSS variables; components use `var(--js-*)`. No logos or other brands' artwork, only the general style. The knob of a switch (Settings) is half of it and light on both sides: `--js-text-muted` on the left when off, `--js-text` on the right of the pink when on (owner, 2026-10-17, #256: "a toggle, but only its color changes"; dark when on, it had the color of the empty half of a switch that is off, and only the left half seemed to change). **Nothing is animated** (owner, 2026-10-11: "just turn all the animations off", after the canvas looked as if it was not being updated in the real window; the cause was not looked for). Our styles and components have no `animation`, `@keyframes`, `transition` (other than `none`), Vue `<transition>`, drag animation of the tab row (`:animation` of vuedraggable) or blinking terminal cursor (but for the blinking dot below), and `src/renderer/src/motion.test.js` fails when one comes back; a change of state or a hover shows at once. Bootstrap's own transitions (its dialogs, toasts and buttons) are not touched. **Two exceptions, both the owner's own.** The first (same day, later: "how about just a faint, hardly visible rotating spinner"): the saving mark in the header is a `b-spinner`, which turns by Bootstrap's own keyframes, so the sweep of our styles does not see it; `motion.test.js` counts the spinners instead and fails on a second one. It is in the page only while a save runs (`v-if`), so nothing turns the rest of the time. The second (2026-10-15, #248: "make the green light of a node blink while it is working"): the green dot of a node blinks while the output of a logged-in session opened from it goes on (`.is-live.is-busy .node.site::after` in `canvas.scss`, keyframes `js-node-busy`: 0.5 s, `steps`, so it switches at once, dimmed to 25 % half of the time and never gone, because the dot still says connected). `motion.test.js` takes exactly these two lines of `canvas.scss` and fails on any other animation or keyframes. The panel watches the output (`createActivityWatch` in `utils/terminal-sessions.js`, fed by the writer of `attach()`): the `busy` of a session turns true at the first output and false `BUSY_IDLE_MS` (1 s) after the last one, with one timer per session, and only these changes are committed (a commit for every piece of output would redraw the canvas and the tab row each time). `busyNodes()` gives the last hop of every logged-in session that is busy, and `markLiveRoutes()` sets `is-busy` on it: not on the jump hosts of the path, never on a yellow or red dot, and an ended or closed session stops at once (`forget`). The 1 s, the 0.5 s and the 25 % are not the owner's numbers. Output is output: the echo of typing blinks too, and so does a program that keeps drawing (a spinner, a clock in a status line). In the real window the canvas is not stale while a dot blinks (`real-window-check-2.cjs busy` reads the frames the window presents: a closed tab and a pan show at once). If the canvas looks as if it is not updated again, these two are the first things to take out. Gone with the animations: the signal that ran along the path of a session (a second `path.flow-path` on every connection), the blinking of the dots on the nodes (back since #248, only on the node of a session with output, see above), the pop of the right-click menu, the rolling band of the CRT background, the fades of the node menu and the popovers. So the states of a path must be told apart standing still (`components/editor/canvas.test.js` checks it with the values of every palette): `markLiveRoutes()` matches terminal sessions (their `hops`, `user@host:port` in path order) against the nodes with `routeStates()` from `utils/terminal-sessions.js` and sets one of `is-connecting` (line and arrow yellow, `--js-connecting`, yellow dot), `is-live` (connected: line in the main color, arrow `--js-signal`, green dot `--js-live`) or `is-failed` (red dashed, `--js-danger`, red dot; the only dashed line, because the red is close to the main pink) on the Rete node and connection views. A line with a session is 4px wide, an idle one 3px. The yellow and the green are the same in every palette on purpose (`--js-sun` is purple in Vapor Blue). It also puts `is-active-terminal` on the node the selected tab was opened from (`activeTerminalNode()`: the last hop of that session, nothing while the panel is minimized): its rule (`.is-active-terminal .node.site` in `canvas.scss`) must stay after the node's `:hover` rule, which changes only colors (owner, 2026-10-11: "change the color instead of moving"; frame `--js-sun`, background `--js-surface-2`, no transform, no other shadow). A node that was clicked while editing (Rete's `.selected`) has no look at all (owner, 2026-10-11: "selecting it does nothing anyway"); Rete still selects it, and `canvas.test.js` fails when a `.selected` rule comes back. This is a look, not a Rete selection (`editor.selected` is untouched, so drag and the node menu act on what the user selected), and the class sits on the view's wrapper element while Rete's own `selected` sits on the `.node` inside it. Locking the editor clears Rete's selection (`clearSelection()` on the `readonly` event), so in a locked space that look can only be the tab's node; the render plugin redraws the `selected` class only on `nodeselected`, so the cleared nodes are updated by hand. Selecting another tab changes no session, so the deep watcher on `terminalSessions` does not fire; `index.vue` watches the computed `activeTerminalNode` as well. While the space is locked a press on a node belongs to the canvas (`utils/locked-press.js`): Rete's node view stops every `pointerdown` on a node before the readonly plugin can refuse the drag, so a drag that started on a node did nothing. `index.vue` listens on `#rete` in the capture phase, stops the press there and dispatches a copy of it on `#rete` itself, where Rete's own canvas drag picks it up; buttons (`PRESS_KEEPERS`) are left alone. Apart from its buttons and the tooltips of its texts a locked node does not answer the mouse (owner, 2026-10-15): the `&.locked` block of `canvas.scss` keeps its look under the pointer (the node of the selected tab needs a rule of its own there, because the locked hover rule outweighs `.is-active-terminal`) and sets the arrow instead of the render plugin's hand on the node and its sockets. The name and the details keep their `title` (`tooltips` in `component.vue`): the owner took the tooltips away with the rest and wanted them back the same day ("can the tooltips show, with only the drag off?", #249). Such a tooltip is drawn by Chromium, not by the page: it hides at a press and does not come back for the same text, so a pan that starts on the text should leave none behind. That is the browser's own behavior and was not measured here (the checks cannot see a native tooltip, and the real window would need the owner's real mouse). Its text cannot be selected with the mouse, locked or not (the render plugin gives `.node` `user-select: none`), and a right click gives the same hint as on the empty canvas. Do not do this with `pointer-events: none` on the node: the buttons appear on `.component:hover`, which needs the mouse on the node. "Connected" comes from an OSC marker (`src/shared/terminal-marker.js`) that ssh prints through `LocalCommand` after login, only in the app terminal and only as a command-line option (a `LocalCommand` in the `-F` config would also run in the ProxyJump `-W` helpers and corrupt the tunnel); the panel reads it with `term.parser.registerOscHandler`. A session ending with 255 counts as failed; other exit codes are the shell's and clear the path.
- Rete v1 places connection ends with `offsetLeft/offsetTop` sums, which skip the borders of parent elements. The node frame is therefore an inset `outline` plus `padding`, not a `border` (`components/editor/canvas.scss`, the canvas look: node box, sockets, connection states); a border on `.node.site` or the socket containers shifts every line off the socket centers.
- Rete v1 fixes the canvas container to pixel sizes (`view.resize()`), only on load and on window resize. The editor component calls it from a `ResizeObserver` on `#editor-area`, because the terminal panel changes the canvas height without a window resize.
- The space scales with the canvas area (owner, 2026-10). The editor remembers the view the user chose together with the area size (`base`); the `ResizeObserver` (on the area only) shows `shownView(base, area)` (`utils/view.js`) and never changes `base`, so every size change is undone exactly. `scaleView` zooms by the ratio of the **heights** and keeps the center centered. It must stay a rule that is its own inverse (A to B times B to A is 1): the first rule took the smaller of the two side ratios, which does not zoom in when only the height grows, so a view chosen while the terminal panel was open stayed small when the panel closed (owner, 2026-10-11: "it does not come back in the same ratio"). The price: a change of the width alone does not scale. A view without a size (the starting view: a space that was never moved and one after Reset view, which `resetView()` remembers as `DEFAULT_VIEW` without a size; also an old file, or one chosen while the area is collapsed) is a view of `DEFAULT_CANVAS` (1010 x 688: the canvas of the default window of 1024 x 768 without the panel, measured on Windows 10 at 125 % with `lists/home-size-probe.cjs` of the checks) and is shown like every view, scaled from that size to the area (owner, 2026-10-17, #265: "after Reset view it does not follow the window, after a small drag it follows in the same ratio: make it consistent", and then "when the window is resized it should be released by itself and go with the ratio"). So the starting view is `DEFAULT_VIEW` only in the default window, larger in a higher one, smaller with the panel open, and scaled around the middle like every view (in a window narrower for its height than the default one, the left edge of the default view goes out of sight). It depends on the area alone, so Reset view pressed again after a change of the window moves nothing, which the rules before it were about. `resetView()` must not give the starting view a size: while the starting view was `DEFAULT_VIEW` in every window, remembering it with the size of the canvas at the press made it follow later changes of the window height like a view the user chose, so the screen after such a change was not what Reset view gave in that window, and the next press moved the space by a few percent and some px sideways (owner, 2026-10-11: "with the terminal on, when I change the height of the program, Reset view is subtly off"). From then until #265 the starting view was the one view that did not follow the window (a view of the canvas without the panel, whatever its size), which the owner found inconsistent. `openView` must not take the area of the moment of opening for a view without a size (the header is a few px higher before a space is open, and the panel of the space may be open). `arrangeNodes()` fits into `fullCanvasIn(area, full)` (`fullSize()`: `#workspace`, the element the area shares with the panel), because what fits the low and wide area gets cut at the sides when the panel closes. Changes made while rescaling (`isRescaling`) are not the user's: they are neither remembered nor emitted as `view-change`. The saved view carries the size as `w`, `h` (`sanitizeView` in `src/shared/view.js`; old files have none and open as before). The header must keep one height while a space is open, or the canvas without the panel has two sizes (a *Show terminals* button with a count badge, 1.2px higher than the others, once did that; the header has no terminal button since 2026-10-12, `views/header-tools.test.js`). It has the same height before a space is open: the name of the app in the title (`.header-brand`) has a line height that keeps it no higher than the name tag; with the default one the header was 5.8px higher and everything under it moved up when the first space opened.
- Connecting nodes is click, click only (owner, #95): the editor vetoes `connectionpick` while a `pointerup` is being dispatched (a window capture listener sets `isReleasing` until the next task), so `rete-connection-plugin` cannot pick a socket on release. Picks on `pointerdown` (start, target, picking up a line) are untouched, with one exception (#202): a left socket is not picked while a left socket is in the hand (`isInputOnInput()`). A click on a left socket without a link puts it in the hand, and a click on a right socket then makes the link; but for a click on another left socket the plugin removes the link of that socket and links nothing (`pickInput`), so a few clicks emptied a space of its links. The plugin does not say what is in the hand, so the editor reads two things: `connectiondrop` names the held socket at every release of the button (before a drop, so the name alone can be stale), and the element in which the plugin draws the line of the hand (`heldLine`, the last child of the canvas right after `use(ConnectionPlugin)`) is empty exactly when the hand is. `socket-check` of the headless checks clicks through it with the real plugin.
- Calculations of the canvas do not overlap (#203): `compile()` in `components/editor/index.vue` is the only way to start one, and `calculate()` (one run of Rete's engine) is called by nothing else. The engine takes no second `process()` while one runs (it warns `The process is busy and has not been restarted`), and the `abort()` that follows it stops the one that runs, so of two overlapping calls neither is finished: the workers do not run, and every node keeps the list of the nodes before it (`prevNodeDataList`: the path of *Connect*, the copied SSH config and the forward summary are built from it) as it was before the change. One click did that: `rete-connection-plugin` replaces a link by removing the old one and making the new one in the same task, and the removal of a node removes its links in the same task. So a call that finds a calculation that has not started yet shares it (the events come before the change and the run starts in a microtask, so the changes of one task are worked out once, after them), and a call during a running calculation gets one that starts when that one has ended, also when it failed. Keep it free of timers: locking waits for `compile()` before it saves, and a real task between the lock and the save would let a window be closed in between (see the saves above). `socket-check` and `loop-check` of the headless checks read that list of every node after such clicks.
- Measuring a node: its view element is only the box. The text under it (`.info-field`, absolute) and the sockets stick out, and the hover menu sits about 39px above it. `extentOf` in `components/editor/index.vue` adds the first two; the menu fits in `ARRANGE_GAP.y` (`utils/arrange.js`).
- A user reads *space* for what the code calls an item, a project or a diagram (owner, 2026-10-15: "*Space* instead of *diagram*, everywhere"; #247): the list and its menu, the header, the hints on the canvas and every message. *Export All Spaces* in the gear menu exports every space, *Export spaces...* of the list the selected ones. The code keeps its names: `diagram` is the node's picture (`img/diagram`, `diagramFilenames`, the field `'diagram'`), and `utils/diagram-data.js`, the store module `diagram`, the ids `#diagram-switcher*`, `projects.json`, the `projects:*` channels and the errors of `normalizeItems` (*Invalid project data.*, only a wrong call shows them) stay. `src/words.test.js` reads every text of the source with `vue-eslint-parser` (strings, template texts and attribute values, not comments) and fails on the word *diagram*; a lone lowercase `'diagram'` is the field and passes. A text put together at run time is not seen there.
- There is no sidebar (owner, 2026-10: any side menu covers the canvas or the terminals; no VS Code layout). Every item has `opened` from `createNavigatorItem` on, 0 for one never opened: added with `$set` at the first opening, it was a change of the list for the `items` watch of the navigator, which saved a second time. The rows of Recent are their own: `.recent-item`, ids `recent-item-N`, outside the `draggable`, no `...` menu, a click (Ctrl too) only opens. The headless checks find the rows of the list by `.list-item` and `.list-item .list-item-name`; keep that class off Recent. - Terminals in the app: `node-pty` is the only runtime `dependencies` entry (native, N-API, prebuilt for Windows/macOS, compiled with node-gyp on Linux), so electron-vite keeps it external and electron-builder packs it (`npmRebuild: false`, `asarUnpack`). `pty.kill()` only signals bash; `killPty` hangs up the whole process group so ssh ends too.
- Sessions are ended one after another on Windows (#215). node-pty 1.1.0 keeps its ConPTY sessions in one list without a lock (`ptyHandles` in `src/win/conpty.cc`): when the program of a session ends, the thread of that session removes it from the list (`SetupExitCallback`, line 106), and when several end at nearly the same moment those threads change the list together and main dies with an access violation in `conpty.node` (seen once in `real-window-check-2.cjs many`, a reload with sixteen sessions: the app was gone; the place was read from the `conpty.pdb` node-pty ships). `lists/kill-many-probe.cjs` of the checks shows it without Electron: 32 sessions ended in one loop killed Node in 3 of 20 rounds, through the old `closeAll` in 1 of 20, and in one loop node-pty's `exit` did not come for one to three of the 32. The thread calls `_$onProcessExit` of node-pty's agent in main once it has removed its session, so `terminal.js` wraps that (`nativeExit`, the session's `released`), and `killInTurn` ends the next session only after that call for the one before, `KILL_WAIT_MS` (2 s) at the latest; `open()` starts nothing meanwhile (a start changes the list too). A session leaves the list and its files go at once, only the pty waits. 32 sessions end in about 0.3 s this way, every `exit` comes, and none died in 20 rounds. Outside Windows sessions are ended at once as before. `terminal.test.js` reads the installed node-pty and fails when that call is gone or the list gets a lock. Not prevented: sessions that end by themselves at the same moment (a server that drops them together) and a resize at that moment (it reads the list). Never kill ptys in a loop again.
- The files of a session (#209): `prepareSession()` writes `<id>.sh` into `<temp>/jumpspace`, and for ProxyJump and forwards `<id>.jmp`, the ssh config (hosts, ports, user names, key paths; never passwords). The script removes them in its `trap cleanup EXIT`, and in the app terminal on Windows that cannot be relied on: when the pty (ConPTY) is closed, the programs in it are ended without a signal, a child before its parent, so bash runs no trap. A closed tab, a reload and the end of the app left the files there, and so did Ctrl+C while connecting (`real-window-check-2.cjs term` on a build without the fix); `sweepTempDir` only takes files older than a day, at the start. So `terminal.js` removes them itself: in `end()` right after `killPty()` (when the app ends no `onExit` comes any more) and in `onExit` (a session that ended on its own). For that `cleanup()` of `prepareSession()` is synchronous and never throws; what it cannot remove is left for the sweep. Removing the script while bash still reads it works on Windows, the name is gone at once. Measured the same day (`lists/close-probe.cjs` of the headless checks): within a second after the close nothing of the session is left, but for 20 to 30 ms the parent of an ended program runs on and sees that program as ended well (after `sleep 3 && mark` the mark was there in half the rounds). For the real sessions that is harmless, after ssh the script only keeps the exit status and exits. A test must not take "the next command ran" for "the program lives on": the real-pty test of `terminal.test.js` measures the time (`SECONDS`), and it runs on Windows since then.

- The pty on Windows (owner, 2026-10-11: "tmux, Claude Code and Codex do not behave correctly, the cursor flashes where the screen moves"). `terminal.js` starts sessions with `useConptyDll: true`, the ConPTY that node-pty ships (`prebuilds/win32-*/conpty/`: `conpty.dll` + `OpenConsole.exe`, Windows Terminal 1.23), and falls back to the one in Windows for good when that spawn throws.
